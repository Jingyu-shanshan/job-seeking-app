## Commands

Run from the repository root. Node `^24.15.0 || >=26` (`.nvmrc` pins 24 for CI and Railway).

| Command | What it does |
| --- | --- |
| `npm ci` | Install all workspaces. |
| `npm run build` | Build `packages/shared` → `apps/server` → `apps/web`, in that order. |
| `npm start` | Run the built Fastify server; it serves `/health`, `/health/ready`, `/api` and the built Angular app on `127.0.0.1:3000` (`0.0.0.0:$PORT` when `NODE_ENV=production`, where `DATABASE_URL`, `BETTER_AUTH_SECRET` and an https `BETTER_AUTH_URL` are required). Loads the root `.env` if present; real environment variables win. |
| `npm run dev:server` | Build shared, then run the server from TypeScript source with `--watch`; loads the root `.env` if present. |
| `npm run dev:web` | `ng serve` on port 4200, proxying `/api` and `/health` to the server on 3000. |
| `npm run desktop` | Build shared and the desktop app, then open it (Electron). It loads the app from `JSA_APP_URL` (default `http://127.0.0.1:3000`, so run `npm start` first); https only, except on loopback. The first run downloads Electron's binary. |
| `npm run runner` | Build shared, then run the local runner (T17) from source. It needs `JSA_RUNNER_TOKEN` (issued on the app's Runner page) and calls `JSA_APP_URL` (default `http://127.0.0.1:3000`; https only, except on loopback), both read from the root `.env`. It starts the installed Google Chrome when the first fill comes; Ctrl+C stops it. |
| `npm test` | Build shared, then run all tests (`node:test` for shared, server, desktop and runner, Vitest through `ng test` for web). Database tests need `TEST_DATABASE_URL`; without it they are skipped locally and fail in CI. |
| `npm run db:migrate` | Apply pending migrations to `DATABASE_URL` (also the Railway pre-deploy command). A second run applies nothing. |
| `npm run auth:create-account -- <email>` | Create the app's one account in `DATABASE_URL` after migrating; asks for the password in the terminal (needs a TTY) and refuses if an account exists. Public sign-up is disabled, so this is the only way in. |
| `npm run migrate:create -w @jsa/server -- <name>` | New empty SQL migration in `apps/server/migrations/`. |
| `npm run db:restore-drill` | `pg_dump` sample data on the `TEST_DATABASE_URL` server, restore it into an isolated database and compare every table. Needs `psql`/`pg_dump`/`pg_restore` no older than the server. |
| `npm run lint` | ESLint (typescript-eslint + angular-eslint) and `prettier --check`. `npm run format` rewrites. |
| `npm run typecheck` | `tsc --noEmit` for shared, server, desktop and runner (web is type-checked by its build). |

Local PostgreSQL (once; the named volume keeps the data across restarts; `docker start jsa-postgres` after a reboot). Port 55432 avoids other local Postgres containers. Copy the two database URLs from `.env.example` into `.env` and add `BETTER_AUTH_SECRET` (`openssl rand -base64 32`), create the dev database, migrate and create your account:

```bash
docker run -d --name jsa-postgres -e POSTGRES_PASSWORD=postgres -p 127.0.0.1:55432:5432 -v jsa-pgdata:/var/lib/postgresql postgres:18-alpine
docker exec jsa-postgres createdb -U postgres jsa_dev && npm run db:migrate
npm run auth:create-account -- you@example.com
```

Single test: `node --test --test-name-pattern "deep Angular route" apps/server/src/app.test.ts` for server/shared/desktop/runner (add `--env-file=.env` for the database tests, e.g. `node --env-file=.env --test apps/server/src/db/schema.test.ts`); `npm test -w @jsa/web -- --include src/app/home/home.spec.ts` for web.

Things that are easy to trip over:

- `apps/server` and `packages/shared` run TypeScript directly through Node's type stripping: relative imports carry the `.ts` extension, and only erasable syntax is allowed (no enums, no parameter properties).
- `@jsa/shared` is consumed through its built `dist/`. After changing it, rebuild (`npm run build -w @jsa/shared`) before the server or web sees the change; `npm test`, `npm run typecheck` and `npm run dev:server` do this for you.
- `apps/web` imports only **types** from `@jsa/shared`, so TypeBox stays out of the browser bundle.
- ESLint forbids importing Fastify or `pg` under `apps/server/src/rules/`. Its first rule is `sources.ts`: `sourcesToRequest` is the only way discovery may pick the sources it requests. `location.ts` decides in-scope / to-confirm / out-of-scope from a job's location text; it runs when the job list is read and is never stored, so a scope change needs no new run.
- Discovery lives in `apps/server/src/discovery/`. An adapter (`Adapter` in `adapter.ts`) lists every open job of one source (`listJobs`) and reads one job's text (`readJob`, T05), and fetches only through `fetchJson` (15 s timeout, 20 MB cap); a `DiscoveryError` message becomes the source's `last_failure_reason`, so keep it user-readable and secret-free. Register adapters in `allAdapters` in `run.ts`; a test requires one for every catalog entry the app requests. Adapters write location text in the one format `rules/location.ts` reads (locations joined by `; `, remote stated in the text, country appended when the site gives it separately) and pass it through `fitLocation`. The rate limiter (one instance made in `app.ts`, shared by discovery runs and JD import, queued per site so concurrent callers stay within the limit) and the one-run-at-a-time guard live in the server process. Tests pass a fake fetch (`src/testing/greenhouse.ts`, `src/testing/ashby.ts`) to `buildApp({ fetch })` or `runDiscovery`, never the real site.
- `job_posting` is one source's listing of one job, refreshed in place by each successful run (one SQL statement per source) and closed when the source stops listing it; a failed run changes nothing. It is not a JD snapshot. Postings of the same catalog entry with the same external id share one `job` row, which is how a job found through several sources counts once. Deleting a source deletes its postings and keeps the `job` rows.
- The source catalog is a constant in `apps/server/src/sources/catalog.ts`, not a table: each entry is one site and one access method, with the date and page of its terms check. Add an entry the app requests only after checking that site's terms; job-alert entries (never requested) record a check where one was made, else `terms: null`. The `source` table stores the user's choices by catalog id; a row whose entry left the catalog is hidden and never requested.
- Job-alert emails (T20) live in `apps/server/src/alerts/`. Each `email_alert` source is one entry of `alertProviders` in `providers.ts` (senders with subject rules and `alertsOnly`, a `jobLink` rule that rebuilds the job's address from its id, an optional `card` rule); adding a source means adding an entry there, never changing the pipeline in `routes.ts`. `rules/alert-email.ts` (`classifyEmail`) decides the source by the From address and subject only. Parsing is postal-mime (`message.ts`); `read.ts` reads jobs only from links the source's rule recognises (decoding a target address that a click tracker carries as a parameter or base64 in its parameters or path), never follows or fetches a link, and keeps no tracking or sign-in parameters; a `card` rule sees the job link's text and the lines before and after it. When no link names the email's job (Snaphunt links only through SendGrid's encrypted tracker; user decision 2026-10-05), an `unlinked` rule reads it from the email's lines: such a job has no address (`alert_job.url` is null, `Job.url`/`JobDetail.url` are null) and is known by a hash of company, title and location in `external_id`; pasting its text requires the job page's link, which becomes its address. The email itself is not stored. Alert sources are on unless their `source` row says otherwise (recruiter messages start off: `onByDefault`); turning one off hides jobs only it listed. Fixtures are made-up emails built with `src/testing/email.ts` that copy the real layouts; never commit a real email. The user's real alert emails are in git-ignored `scratch/t20/` (2026-10-05); `node scratch/t20/check/run-real.ts` reads them all, and its output can be diffed with `scratch/t20/check/real-baseline.txt` after a reader change.
- One job across sites (T20): an address match first, then `rules/same-job.ts` (same company and title, only when exactly one job has that key) over open postings of enabled sources, saved jobs and alert jobs (`discovery/same-job.ts`); pasted jobs never match. Alert imports, desktop saves and discovery runs (new postings join a list-only job) all use it.
- Markdown is excluded from Prettier on purpose (the docs have long hand-formatted tables).
- Schema changes are new SQL files in `apps/server/migrations/` (node-pg-migrate, `-- Up Migration` only; no down section, so they are irreversible). Never edit a migration that has run anywhere. Pending migrations run in one transaction.
- `fact_version` is append-only and `job_snapshot` is never updated except its `last_captured_at`; triggers enforce this, and their `body_sha256` is computed by a trigger (the caller's value is ignored). The `forbid_rewrite(...)` trigger arguments list the only columns an UPDATE may change, so a column added later is immutable unless its migration adds it to that list.
- JD import and summary (T05) live in `apps/server/src/jd/`. A snapshot records where its text came from (`catalog_id`, `paste` for pasted jobs), the https link and the title, company and location as captured; reading the same text again only bumps `last_captured_at`, so the current snapshot is the one read last. Reading a discovered job's text goes through `sourcesToRequest` and the adapter's `readJob`, never at discovery time. `job_requirement` content is immutable (only `removed_at` changes): a user correction removes one row and adds another. `job_summary` and `model_call` are immutable. Quote checks are `quoteFinder` in `rules/quote.ts` (whitespace differences only); unverified items are stored but shown as to-confirm, never as what the JD says.
- `apps/server/src/model/deepseek.ts` is the only code that calls DeepSeek (native `fetch`, JSON output mode, thinking off); the model id and price table are constants with their check date. Every call, failed or not, is recorded in `model_call` with tokens and an estimated cost at the peak price. A summary request carries only the JD text; a match or a draft also carries the facts `mayUse` allows, and nothing else about the user. Without `DEEPSEEK_API_KEY` the summary, match and draft routes answer 503 and nothing else changes. Tests pass a fake through `buildApp({ fetch })` (`src/testing/deepseek.ts` routes other hosts to the fake boards), never the real API.
- Personal facts (T04) live in `apps/server/src/facts/`. `fact.kind` is the category; text, status and the two visibility flags stay on append-only `fact_version`. Only the current (highest-numbered) version may change status or flags; an edit adds a proposed version with both flags off. Whether a fact may go into materials or a model request is decided only by `mayUse` in `rules/facts.ts` (confirmed current version with the flag on, and for the model no email address or phone number per `sensitiveData`); later tasks must select facts through it, never by reading the flags directly. Markdown import (`facts/markdown.ts`) only creates proposed facts and skips text that is already a current version.
- Criteria and matching (T06) live in `apps/server/src/matching/` with the pure rules in `rules/criteria.ts` (`checkJob`) and `rules/match.ts`. `job_criteria` (the old `search_scope`, renamed) is the one row of criteria, and the search scope is the location criterion: `GET/PUT /api/criteria`, there is no `/api/search-scope`. A job's verdict is computed when jobs are read (`checkJobs` in `matching/check.ts`, used by both the list and the job page) and never stored. The must-haves criterion is a preference by default (user decision, 2026-10-02). A match sends only verified, not-removed requirements and the facts `loadFactState` marks sendable (through `mayUse`); `match_evidence` can only cite versions listed in `match_fact`, and the four match tables are immutable (`forbid_change` is the trigger for tables without an `id`). A met/unmet outcome counts only while every fact version it cites is still its fact's current, confirmed version (`outcomeNow`).
- Drafts (T07) live in `apps/server/src/drafts/` with the pure rules in `rules/draft.ts` (answer shape, `draftOutdated`) and `rules/statement.ts` (`statementProblems`, `vocabularyOf`). One click writes one resume or cover letter for the job's current snapshot; the request carries the job's title, company and text and the facts `loadFactState` marks `citable` (`mayUse` for both the model and materials) as refs F1…, never the user's name or contact details (the finished document gets those from app code, T08). A statement is `about` the user (cites fact versions), the job (quotes the job text) or neither (a cover letter's connecting sentence, which may carry no numbers or names); `artifact_claim` places it (`section`, `block`, `line`), `artifact_claim_fact` can cite only versions listed in `artifact_fact`, and the four tables are immutable, so writing again adds an artifact. Which statements go into the document is computed when a draft is read (`checkDraft` in `drafts/load.ts`) and never stored: a fact that changes, is withdrawn or may no longer appear in documents takes its statements out. The checks compare numbers (with qualifiers such as "about"), months, name-like words and limiting words ("expected", "basic") with the cited facts and are deliberately strict: a false rejection is visible, a false pass is not. They do not judge meaning. Writing again is refused while the citable facts are unchanged.
- Form answers (T16) live in `apps/server/src/forms/` (`answers.ts` for saved answers, `job-form.ts` for a job's form) with the pure rules in `rules/form-answers.ts`. Only the user writes answers; no model is involved. A job's form is read on the user's click through the adapter's optional `readForm` (Greenhouse only: `?questions=true`, parsed by `greenhouseForm` into `FormQuestion`s keyed by the form's field names, `email`, `resume`, `question_123`…; an unknown field type fails the read) and kept unchanged in `job_form` (`last_captured_at` only). Which answer fills which question is `fillForm`, computed whenever the form is read and never stored, in this order: the user's answer for that job (`job_form_answer`, valid while the form asks the same wording) → a saved answer (`form_answer`) one of whose wordings equals the question by `wordingKey` and whose places cover the job's location → Your details by field name (links by site) → the job's current kept resume/cover-letter PDF; otherwise `needs_answer` (required) or empty. Never guess an answer (no name splitting, no option that is not exactly one of the form's). A sensitive saved answer, or any compliance/demographic question, fills an optional question only when the user chose so for that job (`answer` null in `job_form_answer`); consents are per job and never saved. T17 must fill from `fillForm` and pause on `needs_answer`.
- The local runner (T17): the server side is `apps/server/src/runner/` (`tokens.ts`, `fills.ts` for the user's routes, `api.ts` for the runner's) with the pure rules in `rules/fill.ts` (`fillFields`, `cannotFill`, `previewFields`, `checkOutcome`, `canHappen`). `/api/runner/*` takes only an `Authorization: Bearer jsa_runner_…` token (the `onRequest` hook in `app.ts` checks it before the Origin check and puts `runnerTokenId` on the request); a session cookie does not open it, a token opens nothing else, and a runner sees only the fills it took. `runner_token` keeps only the SHA-256. A fill (`fill_task`) is started per job by the user, only when `cannotFill` finds no `needs_answer`; it keeps the `fillForm` result of that moment in `fields` (immutable), and the runner fills exactly that. Its status moves only as `canHappen` allows (waiting → filling → paused/filled → closed/failed), with an update conditioned on the status the rule saw; one open fill per job (`fill_task_open`). Each look of the runner (`fill_check`: the page's fields as read back, a PNG ≤ 8 MiB) is immutable, and what each field holds versus the fill's answers is `previewFields`, computed when read. Right after filling, any problem pauses; after the user's Continue only a CAPTCHA or login pauses.
- The runner itself is `apps/runner`, run from TypeScript source like the server (`.ts` imports, erasable syntax only). It drives the installed Google Chrome through `playwright-core` (`channel: 'chrome'`, headed, `chromiumSandbox: true`, a new context per fill) and opens only `https://job-boards.greenhouse.io` pages (`isGreenhouseForm`), the embed form the server builds with the adapter's `formPage`. The page readers in `page-readers.ts` run in the page through `page.evaluate`, so each must be self-contained, and only read; `src/testing/page.ts` runs them in jsdom. `greenhouse.ts` fills: text fields, an option of Greenhouse's searchable selects whose text is exactly the answer (click the select, type, click `react-select-<id>-option-<n>`), boxes ticked through their labels, files (taken only once the page shows `.file-upload__filename`); it must never press Enter, click Submit or write an answer of its own. Greenhouse's form is server-rendered and then hydrated by React: filling before that loses text, opens no select and makes the upload fail, so `task.ts` waits for `formIsLive` (React's `__react…` keys on the inputs) and then for network idle, and `choose` retries until the list opens. The fixture copies all of this (late hydration, file name in place of the input); keep it in step with what real pages do. The app's keys are the page's ids except `location` (`candidate-location`) and `demographic_<n>`. Its API client sends `Connection: close` because Node 26.7's fetch stalls on reused idle connections. `src/browser.test.ts` runs the made-up form `src/testing/greenhouse-form.html` (served for Greenhouse's address inside the browser, never fetched from Greenhouse) in headless Chrome; without Chrome it is skipped locally and fails in CI. Its tests never start the runner against the real site.
- Review and PDF (T08): the user's version of a statement is a row of `artifact_claim_edit` (text and `included`; the latest wins) and is checked by the same `statementProblems` against the same cited facts or quote; `DraftStatement.text` is the current text, `modelText` DeepSeek's, `inDocument` = included and no problems. The finished document is `documentBlocks` in `rules/document.ts`; the web page (`drafts/document-sheet.ts`) renders those blocks and must add no text and nothing that changes how text reads in a PDF (text-transform, letter-spacing, automatic hyphens). An uploaded PDF (`POST /api/drafts/:id/pdfs`, raw `application/pdf` body, 2 MiB) is read with unpdf in `documents/pdf.ts` (the only PDF reader) and kept only when `pdfTextProblems` (`rules/pdf.ts`) finds the document's lines in order with nothing extra and nothing off the page; `document_pdf` and `document_pdf_statement` are immutable. The document page uses `ViewEncapsulation.None` for `@page` (A4, margins, empty margin boxes that keep the browser's own header and footer off) and print-only rules; keep its other selectors scoped to `app-document-page`. Name and contact details live only in the one-row `profile` (`/api/profile`) and are never sent to DeepSeek. Tests make PDFs with `src/testing/pdf.ts`; `src/testing/chrome-resume.pdf` is a real Chrome print of made-up data.
- Each database test file creates and drops its own `jsa_test_*` database on the `TEST_DATABASE_URL` server (`src/testing/database.ts`, excluded from the build). Tests write raw SQL; there is no repository layer yet.
- Use `pool.query()`. A client taken with `pool.connect()` has no error listener while checked out, so a dropped connection would crash the process unless you attach one.
- Every `/api` request except `/api/auth/*` needs a Better Auth session (one `onRequest` hook in `app.ts`, which also runs for unknown routes), so a new route is private without doing anything. Every `/api` write (any method but GET/HEAD/OPTIONS), sign-in included, also needs an `Origin` header from `trustedOrigins`; tests send `origin` and `cookie` headers with `app.inject`. Locally the trusted origins are `http://127.0.0.1:$PORT`, `http://localhost:$PORT` and `http://localhost:4200` (`ng serve`); in production only `BETTER_AUTH_URL`.
- The server needs `BETTER_AUTH_SECRET` whenever `DATABASE_URL` is set; `npm run db:migrate` reads only `DATABASE_URL`. Better Auth's tables (`"user"`, `session`, `account`, `verification`) keep its quoted camelCase names, so quote them in SQL (`select email from "user"`). The `user_single_account` index allows one row in `"user"`. Better Auth logs through Fastify's logger.
- `apps/web` talks to Better Auth's endpoints with `HttpClient` (`src/app/auth/session.ts`), not the Better Auth client library. Routes that need a signed-in user go under the `requireSignIn` parent route in `app.routes.ts`; the guard only decides what to show, the server enforces access.
- The desktop app (T21) lives in `apps/desktop` and is built with `tsc` to `dist/` (ESM main, a CommonJS sandboxed preload `toolbar/preload.cts`, and the toolbar page). Its tests run in plain Node and must never import `electron` (requiring it downloads Electron's binary); keep Electron calls in `main.ts` and logic in pure modules. The page readers in `readers.ts` are sent to the page as source text and run in an isolated world, so each must be self-contained (nothing from outside the function) and only read; `src/testing/page.ts` runs them the same way in jsdom. Third-party pages get no preload and their own session (`persist:browse`); requests to the app go through the app pane's session (`persist:app`) only. Never add code that navigates, clicks, scrolls or types on a third-party page, runs without a user's click, or restores pages at start.
- Jobs saved from the desktop app are in `saved_job`, one row per page address; `rules/job-page.ts` (`jobPageAddress`) turns every LinkedIn address of one job into `https://www.linkedin.com/jobs/view/<id>/`. A saved job with no `job_snapshot` is list-only (`needsText`) and must not be summarised or matched. Their text is a snapshot with `catalog_id` `desktop_save` (or `paste` through `POST /api/jobs/:id/text`).
- Local and CI run PostgreSQL 18. If the Neon project is created on another major version, change the image in `.github/workflows/ci.yml` and the `docker run` above.

## Architecture (planned)

- One Railway service runs Node 24 + Fastify 5 and serves both same-origin `/api` and the built Angular 22 (TypeScript 6.0.x) app (`@fastify/static` with SPA fallback). No second web service, no cross-origin cookies. npm workspaces: `apps/web`, `apps/server`, `apps/desktop` (T21, runs only on the user's computer), `apps/runner` (T17, runs only on the user's computer; a separate process, not part of the desktop app, user decision 2026-10-07) and `packages/shared`.
- `apps/runner` is a local Node process on the user's machine that drives a **visible** Playwright browser to fill application forms. It is never deployed to Railway. It authenticates to the API with a revocable token, takes the fills the user starts, and sends back what the form holds with a screenshot; T18 adds approval, submitting, the result and the receipt.
- Job sources are a catalog the user enables entries from. Four access methods only: `board_api` (public company-board read APIs), `official_api` (a site's official API with the user's own key), `email_alert` (import the job-alert emails a site sends the user) and `manual` (paste). Sites whose terms forbid automated access (LinkedIn) or that have no API for individuals (Työmarkkinatori, 58) use `email_alert`/`manual`; never crawl them or drive them with the user's account. Alert emails are imported by paste or `.eml` upload; the app holds no mailbox credentials. Search scope (Helsinki by default, widening to worldwide) is a user setting independent of the source. Form filling is one adapter per application-form type. Build Greenhouse first for both (decided 2026-09-30), Ashby second. The company watchlist is personal and lives in git-ignored `/vault/watchlist.md`, never in tracked files.
- Model provider: DeepSeek API, called directly for fixed steps (requirement extraction and summary, match explanation, drafts, mapping form questions to existing answers). T05 calls it from `apps/server/src/model/deepseek.ts`; its model id and prices were taken from search-indexed official pages on 2026-10-02 (the docs host was blocked); the real calls that day accepted the model id and parameters, but re-check the prices against the current docs when they matter.
- `packages/shared` holds the TypeBox schemas and their static types shared by API and UI (Fastify validates and serialises with them through `@fastify/type-provider-typebox`, Angular imports the types), so the two can't drift.
- In `apps/server`, the rules (hard-requirement evaluation, claim verification, status transitions) live in a pure module that does not import Fastify or `pg`, so they are testable without a database.
- PostgreSQL (Neon in production) is the primary store via a small plain `pg` Pool, no ORM. Use the Neon **direct** `DATABASE_URL` first, with `sslmode=verify-full` (the server refuses any other `sslmode` in production, because `pg`'s next major version will stop verifying certificates under `require`), handle pool idle `error` events and reconnect after Neon wake-up, and keep TLS certificate verification on (never `rejectUnauthorized: false`). Data-layer tests run against real Postgres (local container or a separate Neon branch), not mocks.
- Migrations: `node-pg-migrate` versioned SQL, including Better Auth's generated tables. They run in Railway pre-deploy (`npm run db:migrate`), never at request or server start. No `db push`, reset, seed or destructive down migrations in production.
- Facts are immutable versions: `fact` (stable identity) plus append-only `fact_version` (text, hash, source, status, visibility). Confirmation attaches to a version; editing creates a new proposed version. Generated claims and frozen applications reference `fact_version` IDs by foreign key instead of copying text. Visibility is two independent flags: may be sent to the model provider / may appear in official materials. T02's tables: `fact`/`fact_version`, `job`/`job_snapshot`/`job_requirement`, `match`/`match_requirement`/`match_evidence`, `artifact`/`artifact_claim`/`artifact_claim_fact`, `application`/`application_artifact`/`application_fact_version`; later tasks add their own columns and tables by migration.
- Auth: Better Auth on PostgreSQL, email and password, one account. Public sign-up is disabled everywhere; the account comes from `npm run auth:create-account`, and every data API checks the server session.
- Attachments (raw JDs, submitted PDFs) live in Postgres (`TEXT`/`JSONB`, size-capped `BYTEA`) with content hashes; never use the container filesystem as primary storage. Markdown/JSON/PDF are import/export formats only.
- `/health` (process) and `/health/ready` (bounded DB query). Bind `0.0.0.0` and read `PORT` on Railway; loopback locally.
- Core domain objects: `Fact`, `Source`, `JobSnapshot`, `Match`, `Artifact`, `ProfileAnswer`, `Approval`, `Application`. Don't build platform services beyond these for V0.1.

## Rules that must not be broken

- Only facts that the user confirmed and allowed in official materials may appear in a resume or cover letter. Submitted application versions are frozen.
- Generation is select-then-render: the model returns structured output where every statement cites fact version IDs, and deterministic code checks numbers, dates and skills against the cited facts. Uncited or failing statements never reach a document. Models never confirm facts.
- JD requirement extraction must quote a verbatim JD span (substring-checked); unverifiable requirements are marked to-confirm and excluded from hard-requirement evaluation.
- Unknown hard requirements are shown as unknown and never counted as met; a model score can't override a known failure.
- Model requests contain only facts flagged as sendable to the provider. DeepSeek processes data outside the EU, so name, phone, email, address, work authorisation and salary expectations never go into a model request; application code writes those fields into documents and forms directly. Choose the Neon/Railway regions with GDPR in mind.
- Raw JD snapshots and submitted materials are never overwritten in place. Generating, exporting or opening a link is not "applied"; only a successful submission or a manual record is.
- The app submits an application only after the user approved **that job**. The approval is bound to the job snapshot, the document hashes and the form answers; any change voids it, and one approval covers one submission. An unknown result is marked to-verify and never retried automatically. Only jobs the user selected are submitted, with a cap per run. No mass applying.
- Form questions without a confirmed answer go to the user; neither the model nor the runner writes answers. Sensitive answers (work authorisation, salary) are used only when that application asks for them.
- The runner never solves CAPTCHAs, never evades bot detection and never stores passwords for third-party sites; it pauses and the user handles it in the visible window. Sites that need a login or forbid automation in their terms (e.g. LinkedIn) are paste-only sources, or saved one page at a time from the desktop app.
- The desktop app (T21) saves only the page the user is looking at, one page per click: a job page's text, or the job entries already shown on a results page (list-only entries are marked as needing the JD and are not summarised or matched until their JD is saved). It never opens pages, scrolls, clicks, types or paginates on third-party sites by itself, never runs in the background, and never imitates human input or evades bot detection (asked for on 2026-10-01 and declined). Third-party cookies and passwords stay in its local session partition.
- JDs, web pages, emails, text on application-form pages and model output are untrusted data and can't authorise reading secrets, changing rules, approving or submitting anything.
- Secrets (`DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `DEEPSEEK_API_KEY`, runner tokens) live only in Railway variables or local protected env. They are visible at Railway *build* time too, so the Angular build must not read or embed them; inspect the final bundle. Enforce HTTPS, Origin checks and request size limits.
- `.gitignore` excludes `/vault/`, `/app-data/`, `/artifacts/`, `/scratch/`, `.env*` (except `.env.example`), `*.db`/`*.sqlite*` and the CV source file names. The repository is public: keep personal data and credentials out of Git, including out of tests, fixtures and docs. Dev and production use different databases or Neon branches.
- Don't rely on Neon alone for backups: schedule `pg_dump` to storage outside Neon and check the plan's point-in-time restore window.
