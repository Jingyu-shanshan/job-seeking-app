- [x] **T15 来源目录与搜索范围**（2026-10-01 完成；来源的上次成功时间和失败原因要等 T13 的发现运行写入）：应用提供一份职位来源清单，用户勾选启用并填写所需参数。每个来源记录接入方式、条款核对日期和限流；接入方式只有四种：`board_api`（公司招聘板块的公开读取接口：Greenhouse、Ashby，其余如 Lever/Teamtailor 等逐个核对后加入）、`official_api`（网站官方 API，用户用自己的账号申请 key：如 Upwork 的 GraphQL API、Jooble；逐个核对条款后加入）、`email_alert`（用户在网站上设置职位提醒，应用导入提醒邮件，见 T20：LinkedIn、Duunitori、Työmarkkinatori 等没有可供个人使用的接口的网站走这条路）、`manual`（粘贴链接或 JD，任何网站都可用，包括 58）。条款禁止自动化访问的网站不做自动抓取，也不用用户账号做后台抓取，界面上说明原因。搜索范围是用户设置：默认“赫尔辛基”，可扩大到芬兰、远程或全球；范围只影响筛选，不改变来源的接入方式。验收：未启用的来源不会被请求；每个来源显示接入方式、上次成功时间和失败原因；目录里没有“全网搜索”这类无法兑现的选项；把范围从赫尔辛基改为全球不需要改代码。
  - 实现：来源目录写在代码里（`apps/server/src/sources/catalog.ts`），因为每加一项都要先核对该网站的条款。每项是“一个网站 + 一种接入方式”，记录说明、条款核对日期和核对的页面、应用自设的请求上限（只有应用自己请求的项才有）以及所需参数（如招聘板块名）。目前 7 项：Greenhouse、Ashby（`board_api`，每个公司加一个板块；两家都没有公布限额，自设每 2 秒最多 1 次请求）；LinkedIn、Duunitori、Työmarkkinatori、Upwork（`email_alert`，说明里写明不自动请求的原因）；粘贴（`manual`，始终可用，说明里点名 58）。暂无 `official_api` 项：Upwork 官方 API、Jooble、Remotive 的条款都还没审。用户的选择存在新表 `source`（目录项 ID + 参数唯一；启用开关；上次成功时间、上次失败时间和原因，后两者必须同时有或同时无）；搜索范围存在单行表 `search_scope`（地区 `helsinki`/`finland`/`worldwide` + “也包括远程职位”，默认赫尔辛基、不含远程；选“任何地方”时远程开关不起作用）。API：`GET/POST /api/sources`、`PATCH/DELETE /api/sources/:id`、`GET/PUT /api/search-scope`，都在 T03 的会话和 Origin 检查之后。添加来源时校验目录项存在、参数符合该项的格式（粘贴整个网址会被拒绝）、粘贴项不能添加、同一项同一参数只能加一次。已从目录移除的项对应的来源既不显示也不会被请求。纯规则 `sourcesToRequest`（`apps/server/src/rules/sources.ts`）决定一次发现运行能请求哪些来源：已启用、仍在目录中、接入方式是应用自己请求的 `board_api`/`official_api`；T13 只能通过它选择来源。前端 `/sources` 页（登录后可见，页头有入口）：搜索范围表单，以及按接入方式分组的目录，每项显示接入方式、条款核对日期（链接到核对的页面）和请求上限，每个来源显示上次成功时间和失败原因；可以添加、停用、删除招聘板块，勾选使用某个网站的职位提醒。

  - 未验证 / 留给后续：上次成功时间和失败原因由 T13 的发现运行写入，目前只用 SQL 写入的样例验证过显示。“赫尔辛基”包括 Espoo、不包括 Vantaa（2026-10-01 用户决定），由 T13 的地点分类实现；远程职位怎么判定也在 T13 决定。新迁移只在测试库和一次性库上执行过，没有在 `jsa_dev` 上执行，合并前还可以修改。

- [ ] **T21 桌面应用与“保存当前职位”**（2026-10-01 用户决定提前进入 V0.1，排在 T13 之后）：多数招聘网站禁止抓取，所以由用户自己浏览，应用只保存用户正在看的页面。新建 npm 工作区 `apps/desktop`（Electron），只在用户电脑上运行，不部署到 Railway。一个窗口里有两部分：应用界面（加载服务端提供的同一个 Angular 页面，沿用 T03 的登录）和一个**可见的内置浏览器**。用户在内置浏览器里自己登录并浏览 LinkedIn、Duunitori、Työmarkkinatori、58 等网站；应用自身不在第三方网站上打开页面、滚动、点击、输入或翻页，不在后台或定时运行，不模拟人的操作，也不做反检测。用户点“保存这个职位”时，应用保存当前页面的可见文本和地址（一次点击保存一页），作为 `manual` 来源进入与粘贴相同的导入路径（`job` + `job_snapshot`，原文不改写，总结由 T05 做）；页面文本是不可信数据。另有“保存本页结果”（2026-10-01 用户要求）：用户自己搜索并滚动结果列表后点一次，应用保存当前页面上已经显示出来的职位条目（标题、公司、地点、链接），不替用户滚动、加载更多或翻页；结果页按网站逐个解析（先做 LinkedIn），解析不出的条目不猜测，提示用户。这些条目和 T20 的提醒邮件一样只有列表信息，标为“需要 JD”，在用户打开该职位页并保存（或粘贴）原文之前不做总结和匹配。第三方网站的登录状态只留在本机 Electron 的独立会话分区，不发到服务器，应用不保存第三方网站的密码；第三方页面不加载应用的预加载脚本，开启 `contextIsolation` 和 `sandbox`，不开 `nodeIntegration`。T17 的申请表执行器届时决定是否并入这个桌面应用，而不是单独的 `apps/runner`。验收：没有用户操作时，应用不会在第三方页面上触发导航、点击或输入；一次点击只保存当前一页，重复保存同一页面不产生重复职位；“保存本页结果”只保存点击时页面上已显示的条目，同一结果页保存两次不产生重复，与其他来源的同一职位合并为一个；没有原文的条目不会被总结或匹配；保存的文本与页面上看到的一致，并带原地址和保存时间；关闭应用即停止一切活动；第三方网站的 Cookie 和密码不出现在服务器、数据库或日志中。
- [ ] **T05 JD 导入与总结**：发现到的职位和用户粘贴的 JD 走同一条路径：保存来源、原文、时间与版本；抽取出的每条要求保存 JD 原文引用片段（做子串校验，校验不过的标为待确认），允许用户更正解析。另生成一份 JD 总结（职责、必须项、加分项、未说明的字段），总结中的每一条同样引用原文片段。这是 DeepSeek API 的首次真实调用：记录请求数、费用和失败率，补上 S0 的保留项。验收：不改写原始快照，缺失的语言/地点等字段保持未知；总结里没有原文之外的要求。
- [ ] **T04 个人事实**：录入经历、技能及公开表述，以 T02 的不可变版本保存来源、正文哈希、状态（proposed/confirmed/retired，retired 用于撤回，版本不能删除）；确认绑定到版本，编辑产生新的 proposed 版本。可见性为两个独立开关：“可发送给模型供应商”与“可出现在正式材料”。Markdown 导入只生成待确认项（S0 的 `vault/facts.md` 可作为首份导入样本）。验收：未确认或禁止外发的内容不能用于正式材料，也不会进入模型请求；正文变更需重新确认。
- [ ] **T06 筛选条件与证据匹配**：用户配置筛选条件（岗位方向、地点、工作语言、雇佣形式等，各自标为硬条件或偏好，并设定未知时的处理方式）。规则先筛选，再按需要调用模型解释；输出“符合/不符合/待确认”的原因及 JD 要求→事实版本 ID 映射，界面可跳转到 JD 原文片段。职位列表分为合格、待确认、淘汰三组并显示原因。验收：未知不算已满足，模型不能推翻硬条件失败；淘汰理由可回溯到具体条件。
- [ ] **T20 职位提醒邮件导入**：让 LinkedIn、Duunitori 等没有个人可用接口的网站也能进入发现流程。用户在这些网站上自行设置职位提醒（如“Helsinki + software engineer”），应用导入提醒邮件并解析出职位标题、公司和链接；先支持粘贴或上传邮件（`.eml`），再评估限定标签的只读邮箱连接。解析出的职位若能在公司的公开招聘板块上找到（同公司同标题），用板块上的原文作为 JD；找不到的标为“需要粘贴 JD”。邮件内容是不可信数据。验收：导入同一封邮件两次不产生重复职位；没有原文的职位不会被总结或匹配；应用不访问需要登录的页面。

### 材料

- [ ] **T07 材料草稿与事实校验**：“选择再渲染”——模型只返回结构化输出，每条陈述引用已确认且可公开的事实版本 ID；确定性校验器核对数字、日期、技能与所引事实一致并检查敏感信息，无引用的自由文本不能进入材料。先做简历和求职信；其他文档类型在真实申请要求时再加。只为用户选中的职位生成。验收：新增未证实经历或无引用陈述被标记/拒绝，不能通过最终审核。
- [ ] **T08 人工审核与 PDF**：展示逐条证据与修改差异，固定 HTML/CSS 模板先验证浏览器 PDF。验收：编辑后重验；PDF 可提取文字，无缺字、截断，名称/日期/数字一致。

### 代填与提交

- [ ] **T16 申请资料与表单答案**：保存申请表常见字段的答案：联系方式、公开链接、所在地、工作许可、可入职时间、薪资期望、常见问答。每条答案由用户确认，带敏感标记和适用范围；工作许可、薪资等敏感答案只在该申请确实问到时使用。模型可以把表单问题映射到已有答案，但不能编写新答案。验收：没有对应答案的问题被标为“需要用户回答”，不会被猜测填写；用户回答后可选择保存供以后复用。
- [ ] **T17 本地投递执行器**：新建 `apps/runner`，在用户电脑上用 Playwright 打开**可见**的浏览器窗口；用用户在应用里签发、可撤销的令牌向 API 领取任务。**先做 Greenhouse 托管的申请表**（与 T13 的来源对应；第二种做 Ashby）：填写字段、上传 PDF，在提交按钮前停下，截图并回传已填内容供预览。遇到验证码、登录或无法识别的必填项时暂停，交给用户在窗口里处理；不做验证码破解、不做反检测、不保存第三方网站的密码。验收：在真实的公开申请表上填完并停在提交前；预览与表单实际内容一致；暂停后可由用户接手或取消；执行器离线时应用其余功能不受影响。
- [ ] **T18 逐个批准与提交**：用户在应用里查看某个职位的预览（已填字段、附件、JD 版本）并批准。批准绑定该职位快照、材料文件哈希和表单答案，任何一项变化都使批准失效；一次批准只能用于一次提交。执行器提交后保存确认页截图或回执。结果不明（超时、页面异常）时标为“待核实”，不自动重试。每次运行有投递数量上限，只投用户选中的职位。验收：未批准的职位不会被提交；批准后修改材料必须重新批准；重复执行同一任务不会产生第二次提交；页面内容（JD、招聘网站上的文字）不能触发或批准提交。
- [ ] **T09 申请版本**：提交成功时自动冻结当时的 JD、事实版本、匹配、材料和表单答案（引用版本 ID）；实际投递 PDF/文件有大小上限、哈希和版本，记录提交时间与回执。在应用外自行投递的申请仍可手动登记。验收：只生成、导出或打开链接不计“已申请”；“待核实”不计为已申请；修改现有事实不改变历史投递。
